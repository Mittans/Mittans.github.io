Assessment 2: QuestForge Part B

QuestForge continues as the same 2-D adventure game, but in Phases 3–4 the engine is extended to allow for more complex interactions, enforce game rules, and the efficiency and performance of your data structures are tested and measured. Movement must validate rules (such as required items or cleared events), Leaderboards must remain correct and persistent, and the engine must be tested for performance and memory behaviour as data sizes increase.

Part B will be assessed by a code review at the end of the semester instead of a viva. In addition to code, there's also some Reflection questions and Screenshots you'll have to provide as part of your complexity analysis. Just like in your Portfolio, make sure these are in Reflection & Screenshot folders respectively, and are clearly labled. Screenshots must be PNG's or JPEG's, and your Reflection notes must be in plaintext (.txt) or Markdown format (.md).

Further, Part B has explicit penalties defined in the rubric for areas like unsufficient Git usage.

 

In Phases 3–4 the focus shifts from “structures exist” to “structures behave correctly at scale”.

  • Rule enforcement: Travel validation (required item present, boss encounter cleared, correct adjacency); Combat queue tracking (combat must continue until someone wins or flees); Combat order enforcement (players and enemies can't take more than 2 actions per turn); and GameEvent interrupts (player can take certain actions after peeking the next pending event). These rules sit on top of the same underlying collections and must be applied consistently.
  • Observability: Conduct tests on code execution time using Stopwatch (System.Diagnostics.Stopwatch) and measure memory usage using the GarbageCollector (GC.GetTotalMemory) to produce growth graphs for critical operations at various scales (e.g. creating 100 items, 1,000 items, 10,000 items, etc.).
  • Testing: In addition to regular unit tests for classes and methods you write, you also need to have a test that plays a complete sample game, and includes all the classes and functional requirements found in Phases 1 - 3.
  • Analysis: Contrast observed timings/memory against the expected behaviour of the underlying structures and operations, and justify mismatches (for example, hashing cost, allocation patterns, resizing effects).

The engine remains a library with console demonstrations and an xUnit test harness. You are still not building a game UI, or playing the game using console input (although you certainly can if you feel like the extra work).

For Phase 3 and 4

Once the structural pieces and basic interactions of the engine exist, the real integration challenge begins. It is one thing to make the individual parts of the system work; it is another to make them work predictably and efficiently together.

Part B also asks you to analyse how the game engine performs. Programming is often about identifiying weird edge-cases, bottlenecks, and making trade-offs. While these issues might be easier to ignore for simple programs, without the benefit of many years of experience, often these issues can only be understood after you've made the mistake. To help you understand some of these issues, you will create a large amount of data, and measure execution time and memory usage of your code.

The skills developed here are not theoretical extras. These are the same techniques used in industry when diagnosing slow systems, memory leaks, or unpredictable behaviour. By the end of this assignment, you will understand not only how to build data structures, but have some insight on their performance and more experience to make informed choices about what approach fits the problem at hand.

Core requirements

 

Phase 3 – Traversal rules, Combat Logic, GameEvent interrupts, the Leaderboard

Subsystems: 

  • Travel checks & Player movement
  • Combat logic & round based combat
  • Event logic and player interrupts
  • Leaderboards & score tracking

Implement: 

1. Travel rules + GameEvent Interrupts

  • Implement CanMove(), AddRequirement()
  • Update MovePlayer() method to enforce CanMove()
  • Implement PeekEvent() and Interrupt()
  • Player is limited to 1 Interrupt() per Zone
  • At a minimum, implement an Interrupt GameEvent for using an Item.

3. Leaderboard (SortedSet<Player>): 

  • Track and update player score
  • Insert score
  • Maintain Top 10 (persistent, across relaunches, save the file somewhere)
  • Print rankings

4. Combat integration

  • Combat logic fully implemented and integrated.
  • Combat continues until a GameEntity wins or loses.
  • Handling for Player or Enemy Fleeing.
  • Transition to Scoring and Leadboard logic if Player loses.
  • Combat log kept.

Focus: measurement, scalability, comparison.

Subsystems: All from Phases 1–3.

You can use Program.cs to run the performance tests, or create a seperate .cs file in your testing project, it doesn't matter. Ensure the performance tests output their results to the console when run.

Implement:

  • Zone manager that creates and adds 10, 100, 1_000, 10_000, 50_000 Zones. For each Zone added, make sure you add it into the middle of the Zone list.

Functional Requirements (Phase 3)

This list of function requirements are functions you must include in your code. The list isn't comprehensive, but should give you a good overview of what's required. Phase 3 includes many functional requirements from Phases 1 & 2 that have been updated with a new description to reflect their additional requirements. Same principles as Part A apply, where you may deviate slightly from these function signatures, provided you have justification in your Reflection notes. 

Function Description

 

ZoneManager.AddRequirement(Zone zone, List<GameEvent> requiredEvents, List<Item> requiredItems) → void

 

Add a requirement to travel to the given Zone. One List might be empty (e.g. if only an Item is required). At least one List much be non-empty. Input is the list of required GameEvents and Items. You'll need to think about how you are going to track whether a player has cleared a GameEvent

Player.CanMove(ZoneManager zm, string toZone, List<GameEvent> playerEvents, List<Item> playerItems) → bool Allowed

Use the ZoneManager to check the requirements and adjacency of the toZone and return whether the Player is permitted to move. Input is the Players list of cleared GameEvents and inventory Items.

Player.MovePlayer(ZoneManager zm, string toZone, List<GameEvent> playerEvents, List<Item> playerItems)  → bool Success

Check the value of Player.CanMove() to validate travel rules, then move the Player.

Player.Interrupt(ZoneManager zm, Item item) → bool Success

Player may interrupt the currently pending event to use an Item. For example, using a potion before a combat event. Player should be limited to 1 Interrupt per Zone. Method returns false if invalid Item is passed in, or Player has already used their Interrupt.

Player.AddScore(int amount) → int CurrentScore

Add score to Player's total.

LeaderBoard.AddScore(Player player, int score) → void

Use a SortedSet<Player> to maintain a Leader-board of Player scores. The Leader-board should be persistent between sessions.

LeaderBoard.Initialise() → void

Clear and/or Initialise the Leader-board with some default or dummy scores.

GameManager.SaveRankings(string filePath) → bool Success

Serialises the current LeaderBoard as JSON and saves it to the filesystem.

GameManager.LoadRankings(string filePath) → LeaderBoard obj

Reads the JSON file from the filesystem and deserialises it into a LeaderBoard object.

GameManager.RegisterScore(Player player) → bool madeTheCut

Register the Player's current score to the Leaderboard. After registering, returns a boolean if the Player made the Top 10 Leader-board.

GameManager.PrintTopTen() → string Result

Pretty print the current top 10 Rankings.

CombatManager.BeginCombat(GameEntity obj1, GameEntity obj2) → GameEvent? Result

Begin a complete combat between two GameEntities. Continue combat until a Defeat or Flee GameEvent is received from one of the GameEntities. You'll have to think about how each round will permit the GameEntity to submit their moves for the turn, and how to handle intermediate states.

CombatManager.GetLog() → string Result 

Returns the full log for the current combat encounter as a string (with formatting).
