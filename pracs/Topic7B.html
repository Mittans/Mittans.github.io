Task 5: Logging Basics (Optional):

(It took me until after the first classes to get this Task ready, so it's optional. It's still worthwhile to know, though)

One of the sore points for Logging in C# (at least in my opinion) is that it only comes in 2 flavours -- very basic and industrial strength.

If you take a look the docs: https://learn.microsoft.com/en-us/dotnet/core/extensions/logging/overview

You'll see Microsoft doesn't provide a native Logging package and instead relies on some NuGet packages, and is mostly concerned with the industrial strength application.
So what can we do if we don't need the fancy stuff and just want a little bit of logging for our application?

One Option is just to rely on terminal features to capture the output of your program.
You might do this when you're running a program on a server, and won't have eyes on the output. Instead to you can capture that output to a file, and check it later.

  1. Make sure your Program.cs / Main method includes some Console.WriteLine() outputs
  2. Use the VS Code Integrated Terminal to do dotnet run just to make sure you're in the right folder
  3. do dotnet run > log.txt and check to see the log.txt output

Helpful, huh? By using the > symbol, we're telling dotnet run to redirect the output from the terminal into a file.
Be aware that this is a redirect, so it's writing the output to the log instead of to the Console.

One thing to note, is that this won't capture some types of output. For example, try this:

  1. At the end of your Program.cs, after you've written everything you need to the Console, let's introduce an exception to simulate a bug.
  2. Throw a basic Exception: throw new Exception("Encounted a bug, exiting the program.");
  3. Do dotnet run > log.txt and check to see the log.txt output.
​

Reflection

  • Where was the Exception text written? To the Console or the log.txt?
  • What happened to the contents of log.txt? Did the program append to the log and overwrite it?
  1. To fix the first point, we can do dotnet run > log.txt 2>&1
  2. And to fix the second point, we can do dotnet run >> log.txt 2>&1

Run the commands to check they work, and then answer the questions.

 

Reflection

  • What on earth does adding 2>&1 mean? Why does it fix our problem?
  • How is >> different to > ?

Output

  •  Screenshot of your log.txt showing both regular output and error output has been captured.

(If you're wondering how to output text to both the Console and a file, you can use the tee command. Although this might be Mac / Linux only: dotnet run 2>&1 | tee -a log.txt) 

Ok, while this is a good start. It's not really a good log because there's no metadata attached to it.

Typically, we'd at least like our logs to include a timestamp, as well as some sort of categorisation (e.g. is it an info message or critical error).

Adding this metadata means if we know the server was having problems at 1am on Tuesday the 1st of May, we can go searching through our logs for only "Error" tagged messages that happened around that time, instead of sifting through everything.

 

Now, let's install the Logging package. Process is the same as ScottPlot in the last prac: https://www.nuget.org/packages/Microsoft.Extensions.Logging

Next, import it into your Program.cs:

using Microsoft.Extensions.Logging;

Now setup the logging factory (required, and unfortunately overkill for our app). Chuck the following lines at the start of your Main() method:

using var loggerFactory = LoggerFactory.Create(builder =>
  {
    builder
    .SetMinimumLevel(LogLevel.Debug)
    .AddConsole(options =>
     {
        options.FormatterName = "simple";
     }).AddSimpleConsole(options =>
     {
      options.TimestampFormat = "yyyy-MM-dd HH:mm:ss ";
      options.SingleLine = true;
     });
   });

ILogger logger = loggerFactory.CreateLogger("Program");

Now let's try outputting some logs! Try some of logger's methods:

logger.LogInformation("Hello World");

In addition to LogInformation(), we have various log levels, like LogDebug(), LogWarning(), LogError() and LogCritical()
